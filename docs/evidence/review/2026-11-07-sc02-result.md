# SC-02 database outage review — 2026-11-07

## Scope

This review records one complete local database-stop experiment and one
interrupted attempt. It is evidence for the local kind/Supabase test bed only;
it is not a production availability or data-loss claim.

## Runs

- `sc02check3`: read-only preflight passed after the local observability stack
  was restored.
- `sc02smk9`: 30-second smoke passed with 150/150 validated sales and 150
  matching ledger rows; no duplicates, lost responses or unmatched tags.
- `sc02a`: invalid. The control gate passed and the database stopped, but the
  operator process terminated during the 480-second hold. The database and
  observability stack were restored manually; no recovery verdict is derived.
- `sc02b`: valid complete run. The same Postgres container was stopped for the
  declared hold and started without restarting the Tawira deployment.

## `sc02b` result

The control gate sent 602 requests and passed with 100% validated sales, p95
latency 650 ms and p99 latency 1,082 ms. The full 1,350-second load sent 6,750
requests. It produced 4,305 validated sales and 2,445 HTTP 200 application
errors while the database was unavailable or becoming ready.

The fault-relative recovery result was 510 seconds at 30-second window
resolution. The independent DB-ready-relative result was 30 seconds, within
the 300-second target. The first DB-ready window reached 93.29%; the next full
window reached 100%.

The ledger export contained 4,306 rows and 4,306 distinct request tags. There
were no duplicate or unmatched database tags, but one response was not matched
to a validated acknowledgement. That is a lost-response signal, so retry and
idempotency safety remains unresolved even though the database rows reconcile.
The three Tawira replicas remained Ready and did not restart during `sc02b`.

## Detection evidence

The exported firing-alert range contained no firing series. A separate alert
range contained nine samples for `HighLatencyP99` in `pending` state. The
runner's sampled alert history and the Prometheus ranges establish observed
alert state only; they do not establish notification delivery or prove that a
rule never qualified between samples. No dashboard screenshot was captured for
this run, so the machine-readable Prometheus exports and timeline are the
authoritative telemetry artifacts.

## Reproduction

```bash
  measurements/results/sc02b/client.jsonl \
  measurements/results/sc02b/ledger.json
node measurements/scripts/windows.mjs measurements/results/sc02b
```

The raw run directory preserves `run.json`, `job.json`, `control-result.json`,
`events.log`, `timeline.jsonl`, `client.jsonl`, `ledger.json`, `reconcile.json`,
`windows.txt` and the Prometheus alert-range exports. The source and generator
hashes, image digest, database image and migration list are recorded in
`run.json`.

## Follow-up

Repeat with a fresh run ID after investigating the single lost response. Keep
the fault-relative and DB-ready-relative anchors separate, and treat any
acknowledged missing or mismatched UUID as a stop condition. Do not promote
this one local observation to a general RPO or idempotency claim.
